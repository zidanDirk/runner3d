# Runner3D Beta 试玩与实机验收

本阶段准备小规模、受邀的 5～10 人试玩。自动化机器人和 Playwright 移动视口只提供工程证据，不计为真实试玩者。公开访问地址、HTTPS、收集地区、试玩负责人和接收反馈渠道均须由发布负责人确认；这些配置完成之前不能宣布公开 Beta 上线。

## 试玩安排

第一批至少覆盖桌面浏览器、iPhone Safari、Android Chrome。建议招募 2～4 名桌面玩家、2～3 名 iPhone 玩家和 2～3 名 Android 玩家，可按实际人数调整。不要为了完成配额把模拟浏览器记为真实设备。

每人先独立试玩，观察者不额外解释操作，只记录卡住的步骤。可以使用试玩者编号 T01～T10；不要求姓名、联系方式、登录或精确位置。录屏、录音或额外个人资料必须另行告知并由组织者处理，本项目不会自动上传这些内容。

依次观察以下真实流程：

1. 打开受邀版本；找到开始按钮。
2. 自行决定查看、完成或跳过新手引导。
3. 开始第一局，尝试换道、跳跃和滑铲。
4. 尝试收集金币与道具；记录是否理解其用途。
5. 自然失败后查看结算；询问是否理解失败原因。
6. 打开商店，理解升级费用和实际作用；余额不足可以正常返回。
7. 打开任务，观察是否理解完成条件与领取方式。
8. 再次开始一局；记录是否主动愿意再玩。
9. 打开设置，调整画质、声音或操作方式，然后手动继续。
10. 从首页、设置或结算打开反馈，选择类型并生成文本；自愿附带诊断后预览，再复制或下载交给试玩组织者。

观察问题包括：开始入口是否明显、左右/跳/滑是否容易掌握、金币用途是否清楚、失败解释是否有帮助、升级效果是否容易感知。不要把引导后的成功当作独立发现，也不要把事件次数比例称为玩家留存率。

## 反馈机制与隐私

当前默认是**本地手动反馈**，没有接收后端。界面显示“尚未发送”，生成、复制、下载均不表示服务器收到。组织者应提前告诉试玩者文件交给谁；没有明确接收方时，用户可以保留文本，不能出现虚假的在线提交成功。

反馈共七类：操作、画面、性能、音效、难度、功能建议、其他。内容限制为 5～1000 个 UTF-16 单位，与浏览器 `minLength` / `maxLength` 一致。请勿写姓名、手机号、邮箱、账号或其他私人信息。内容只在当前表单内存中保留，不写 localStorage，不进入错误监控和行为分析；关闭页面会丢弃未保存草稿。

版本、Build ID 和发布环境作为反馈基本字段始终在表单中可见，便于定位构建，不含玩家身份。其他诊断默认不附带。主动勾选后，完整 JSON 会显示在表单中，生成文本只附带可见的白名单字段：版本、Build ID、发布环境、浏览器大类、画质、最多五个错误代码，以及 FPS/平均帧时间/P95 的粗粒度数值；没有样本的指标为 null（N/A）。不附带完整存档、网址和参数、错误原文、完整 User-Agent、截图、精确设备标识或 GPU 内存推测值。

`src/beta-feedback/schema.ts` 负责白名单校验和文本格式，`adapter.ts` 定义可替换的 `FeedbackAdapter`，`src/ui/BetaFeedback.tsx` 负责表单。默认 `manualFeedbackAdapter` 不联网。重复点击最多保留一个在途请求；同一份已处理内容不重复提交，失败可以重试，手动文本仍可重新显示。未来接入远程服务前，必须确定目的地、数据说明、保存期限、清除方式、发布地区及所需授权，不得仅在客户端填一个密钥就开启服务。远程适配器只有在服务明确确认接收后才能返回 `accepted`。

```sh
npm test -- tests/unit/beta-feedback.test.ts
npm run test:e2e
npm run release:check
```

浏览器验证需实际打开三个正式反馈入口，覆盖默认不附带、诊断全文可见、输入限制、重复点击、复制失败降级和窄屏滚动。远程适配器的失败测试使用隔离测试数据，不读取或更改真实玩家钱包。
